### Architecture Decisions

1. **Reversibility**: Assertions marked as `'infeasible'` can be reverted to `'pending'` if later found to be feasible
2. **Coverage Integrity**: After marking assertions infeasible, coverage is re-validated to ensure no orphan assertions remain
3. **Audit Trail**: The `notes` field records why an assertion was marked infeasible, maintaining traceability
4. **Database-driven**: All state changes are persisted to SQLite for durability

### Integration Points

- **PlanAdjuster**: Extends existing interface, compatible with feat-006 (Scenario 1)
- **CoverageValidator**: Backward compatible - infeasible assertions simply don't participate in validation
- **IssuesHandler**: Can be integrated to handle `assertion_infeasible` category issues
- **Database**: Schema changes are additive and backward compatible
